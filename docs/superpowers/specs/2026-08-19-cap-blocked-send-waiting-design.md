# Design: Cap-blocked send waiting system

**Status:** Approved for planning.

## Problem

An email whose content already exists — generated by the write pipeline, or explicitly approved by a client in `/inbox` — can still hit `RATE_LIMITED` at the actual send (`sendViaMailbox`) because the daily cap, the Mailreach warmup gate, or mailbox health changed between an up-front probe and the real atomic send. Today every one of these paths reacts the same way: `markEmailFailed`. That's wrong for a cap/gate/health condition — it's transient and will resolve on its own, but the codebase treats it identically to a genuine delivery failure (revoked auth, provider rejection):

- **`write.ts` (`processLead`, `auto_send`/`hybrid`)** — a multi-lead case where one lead sent and a second lost a same-tick cap race ends up `contacted` (case-level, correct — outreach did happen) with the second lead's real, already-written content permanently marked `failed`. Nothing ever revisits it without a human noticing (traced end-to-end 2026-08-19, see `.claude/roadmap.md`).
- **`approveDraft` (inbox/actions.ts, `human_approve`)** — a client explicitly clicks Approve on specific wording; if the send hits the cap, that exact approved content is discarded. The case does get flagged `waiting`/`daily_cap` (fixed 2026-08-19), which makes it eligible for write-fanout's auto-retry — but that retry runs the full write pipeline again, **regenerating fresh wording via the LLM**. The client's approval is silently overridden by different text they never saw, which violates an explicit constraint on this system: client-approved content must never be altered after approval.
- **`followup.ts` (`runFollowupStep`, all modes)** — worse than both: `RATE_LIMITED` marks the row `failed` and returns `'skipped'` with **no reschedule at all**. No cron sweeps sequences directly, so a cap-blocked follow-up step is permanently lost — the sequence just stops advancing, silently, forever.

All three are the same root cause: **a transient mailbox-availability failure on already-committed content is handled identically to "this content is broken and needs regeneration."** It never should be — regenerating discards real work (an LLM call, or worse, a client's explicit approval) for no reason; the fix is always "send the same thing again once the cap allows it."

## Scope decisions (from brainstorming)

- The dividing line is **whether content already exists on the row**, never which `reply_mode` produced it. A case blocked *before* any generation happened (today's up-front eligibility probe in `runWriteForCase`, see `docs/superpowers/specs/2026-08-17-outreach-send-waiting-system-design.md`) is unaffected by this design — regenerating fresh content on that retry is correct and desirable, since nothing was ever shown to anyone.
- First-touch (step 0, across `auto_send`/`hybrid`/`human_approve`) **and** follow-up cadence steps (`followup.ts`, all modes) are both in scope — the follow-up gap is worse than first-touch's and shares the identical fix shape.
- Priority ("waiting" content sends before today's brand-new work once the cap resets) is enforced by keeping the drain sweep on the same cadence as write-fanout, not by merging the two crons into one. This is a soft, not hard, guarantee — see §6.
- `resend-failed.ts` / `/api/pipeline/resend-failed` keep their existing file and route names despite the widened scope (first-touch-only failed-email resend → all-steps waiting-content drain) — nothing about this mechanism is live in production yet, so a rename isn't worth the churn. Comments and docstrings are updated in place to describe the new semantics.

## 1. State model

New `email_status` value **`'waiting'`**: content exists (subject/body/thread info already committed to the row), a real send was attempted and hit `RATE_LIMITED`, will be retried as-is by the drain sweep. Distinct from `'failed'`, which now means exclusively "a real delivery error occurred — not auto-retryable, may need a human."

```sql
-- supabase/migrations/0051_email_waiting_status.sql

-- ALTER TYPE ... ADD VALUE cannot share a transaction with anything that
-- references the new value (PG12+ restriction) — same lesson as migration
-- 0049's split (see .claude/roadmap.md 2026-08-19). This file does nothing
-- but add the value.
alter type email_status add value if not exists 'waiting' after 'queued';
```

New `case_wait_reason` value **`'awaiting_resend'`**: the case has at least one lead whose first-touch content already exists and is parked at the email level in `'waiting'`; it will clear when the drain sweep successfully sends it, never by regenerating. Deliberately excluded from `AUTO_RETRY_WAIT_REASONS` — write-fanout's cron must never reclaim a case for fresh writing just because one lead's real content is waiting on cap.

```sql
-- supabase/migrations/0052_case_awaiting_resend_reason.sql (separate file/transaction, same reason as above)

alter type case_wait_reason add value if not exists 'awaiting_resend';
```

`src/types/database.ts`: `email_status` gains `'waiting'`; `case_wait_reason` gains `'awaiting_resend'`. No column/constraint changes — `cases.wait_reason` and `emails.status` already accept any enum value.

**Look right so far?** *(confirmed)*

## 2. `markEmailWaiting` (`src/lib/db/emails.ts`, new function)

Mirrors `markEmailFailed` exactly, targeting the new status:

```ts
export async function markEmailWaiting(
  supabase: SupabaseClient<Database>,
  id: string,
): Promise<void> {
  const { error } = await supabase.from('emails').update({ status: 'waiting' }).eq('id', id)
  if (error) {
    throw new AppError('DB_ERROR', 'Failed to mark email waiting', { id, cause: error.message })
  }
}
```

`reclaimFailedOutboundEmail`'s `.eq('status', 'failed')` guard is **unchanged** — a `'waiting'` row does not match it. This is the safety backstop: even if a case is mistakenly re-dispatched into `runWriteForCase` while a lead's content sits `'waiting'`, `claimOutboundEmail`'s upsert (conflict, `ignoreDuplicates`) returns nothing and the reclaim fallback also returns nothing (wrong status), so `processLead`'s `claimed` is `null` and the lead is skipped — never overwritten.

## 3. `write.ts` — no regeneration on a same-tick cap race

`processLead`'s catch:

```ts
} catch (error) {
  await markEmailWaiting(supabase, claimed.id)
  if (error instanceof AppError && error.code === 'RATE_LIMITED') return 'waiting'
  throw error
}
```

(Non-`RATE_LIMITED` errors still go to a `markEmailFailed` path — a real delivery error is not auto-retryable content-preserving territory. `processLead`'s return type gains `'waiting'` alongside `'sent' | 'drafted' | 'skipped'`.)

Per-lead pre-filter added to `runWriteForCase`'s leads loop, before calling `processLead`, to avoid paying for an LLM call whose claim will just no-op:

```ts
const waitingLeadIds = await listWaitingLeadIds(supabase, input.caseId) // new lib/db/emails.ts helper: distinct lead_id where case_id = X, sequence_step = 0, status = 'waiting'
for (const lead of leads) {
  if (waitingLeadIds.has(lead.id)) continue
  // ...existing processLead call...
}
```

Post-loop status decision drops today's eligibility re-check (no longer needed — the outcome is identical regardless of *why* it was rate-limited):

```ts
if (sent > 0) {
  await updateCaseStatus(supabase, input.caseId, 'contacted')
  await enqueueCrmSync(input.caseId, 'contacted')
} else if (drafted > 0) {
  await updateCaseWaiting(supabase, input.caseId, 'awaiting_manual_approval')
} else if (waiting > 0) {
  await updateCaseWaiting(supabase, input.caseId, 'awaiting_resend')
} else {
  await updateCaseWaiting(supabase, input.caseId, 'no_viable_leads')
}
```

## 4. `approveDraft` (inbox/actions.ts) — simpler than today's fix

```ts
} catch (error) {
  if (isAppError(error) && error.code === 'RATE_LIMITED') {
    await markEmailWaiting(supabase, email.id)
    try {
      await updateCaseWaiting(supabase, email.case_id, 'awaiting_resend')
    } catch (waitError) {
      await logEventSafe({ /* ...unchanged shape... */ })
    }
    revalidatePath('/inbox')
    return // not a failure — approval succeeded, send is parked. See §7.
  }
  try {
    await markEmailFailed(supabase, email.id)
  } catch { /* best-effort */ }
  revalidatePath('/inbox')
  throw error
}
```

No more `getClientById`/`getOutreachEligibility` re-check in this catch — the reason no longer changes what happens. This *replaces* the 2026-08-19 fix (which flagged `daily_cap`/gate/etc. and still routed through the regenerating auto-retry path) rather than layering on top of it.

The existing post-send bookkeeping below the try/catch (`scheduleFirstFollowup`, `claimCaseContacted` + CRM sync) is unchanged and still only runs on an actual send — the `RATE_LIMITED` branch returns early, before reaching it, exactly as a thrown error did before. The function's final line changes from an implicit `undefined` return to `return { status: 'sent' }`, after that existing bookkeeping completes.

## 5. `followup.ts` — the worst-off path gets fixed, not just improved

`runFollowupStep`'s catch:

```ts
} catch (error) {
  await markEmailWaiting(supabase, claimed.id)
  if (error instanceof AppError && error.code === 'RATE_LIMITED') {
    return { sequenceId: sequence.id, action: 'skipped' }
  }
  throw error
}
```

No reschedule call here — unlike the paused-campaign branch above it in the same function, this step doesn't need one. The row now sits `'waiting'` with its content already committed; the drain sweep (§6), not a QStash republish, is what revisits it. The sequence's own `current_step`/`next_action_at` stay exactly as they were pre-attempt, which is correct: as far as the sequence is concerned, step N hasn't completed yet.

## 6. The drain sweep (`resend-failed.ts`, widened scope)

`listFailedFirstTouchEmails` → `listWaitingOutboundEmails(supabase, limit)`: same shape, `status = 'waiting'`, **no `sequence_step = 0` filter**, ordered oldest-first (unchanged — this ordering is what gives waiting content priority over same-day fresh work, see §7).

`resendOne` branches on `sequence_step`:

- **`=== 0`** (first-touch): unchanged from today's implementation — claim, `sendViaMailbox`, `scheduleFirstFollowup`, flip case to `contacted` if not already.
- **`> 0`** (a follow-up step): loads the lead's active sequence (`getSequenceByLeadId`, new — see below), recomputes `inReplyTo`/`threadId` from `listThreadEmails(leadId)` exactly as `runFollowupStep` does at generation time, resends the row's already-stored subject/body via `sendViaMailbox`, then runs the same tail bookkeeping `runFollowupStep` runs on a normal send: final step → `stopSequence` + `updateCaseStatus(caseId, 'dead')` + CRM sync; otherwise → `advanceSequence` + `publishJsonWithDelay` the next step at its configured cadence delay.

A `RATE_LIMITED` outcome on the resend attempt itself calls `markEmailWaiting` again (stays parked, retried next tick) instead of `markEmailFailed` — matching every other path in this design. A genuine delivery error still marks it `failed`.

`src/lib/db/sequences.ts` — new function:

```ts
// Single active sequence for a lead — the drain sweep's only lookup that
// isn't already covered by an id- or case-scoped existing function.
export async function getSequenceByLeadId(
  supabase: SupabaseClient<Database>,
  leadId: string,
): Promise<SequenceRow | null> {
  const { data, error } = await supabase
    .from('sequences')
    .select('*')
    .eq('lead_id', leadId)
    .eq('state', 'active')
    .maybeSingle()
  if (error) {
    throw new AppError('DB_ERROR', 'Failed to load sequence by lead', { leadId, cause: error.message })
  }
  return data
}
```

## 7. Cron cadence and priority

Per the brainstorm decision, the drain sweep stays a separate cron from write-fanout rather than merging into one tick — simpler, no changes to write-fanout's own tested code path. To keep the priority guarantee ("waiting content sends before today's brand-new work") reasonably tight without a hard merge, the drain sweep's cadence drops from hourly to the same 5-minute cadence as write-fanout: `scripts/schedule-resend-failed-cron.ts`'s default cron expression changes from `'0 * * * *'` to `'*/5 * * * *'`.

This is **not** a hard guarantee — both crons independently call into the same per-mailbox cap pool (`sendViaMailbox`'s atomic `claim_mailbox_send`), so whichever cron's tick actually executes first in a given 5-minute window claims cap slots first. In practice the gap after a UTC-midnight cap reset shrinks from up to ~59 minutes (today's hourly cadence) to ~5 minutes. If this proves insufficient in practice, the fallback is the merged-single-tick approach discussed and declined in brainstorming — revisit then, not preemptively.

## 8. Client-facing UX (`/inbox`, i18n required — client-facing per project rules)

`approveDraft`'s `RATE_LIMITED` outcome is no longer an error — the approval succeeded, the send is parked. `draft-row.tsx`'s catch around `approveDraft` needs to distinguish this from a real failure so the toast is honest. Since `approveDraft` now returns normally (not throws) on `RATE_LIMITED` (§4), the existing try/catch's `catch` block only ever sees genuine failures — but the success path currently always shows `toastEmailSent` ("Email sent"), which is also wrong when the send was actually parked. `approveDraft` needs a discriminated return value so the caller can tell the two success outcomes apart:

```ts
// actions.ts
export async function approveDraft(formData: FormData): Promise<{ status: 'sent' | 'waiting' }> {
  // ...
  // RATE_LIMITED branch: return { status: 'waiting' }
  // normal send-succeeded path: return { status: 'sent' }
}
```

`draft-row.tsx`: on `status === 'sent'`, unchanged `toastEmailSent`. On `status === 'waiting'`, new toast key. New strings in both `src/messages/en.json` and `src/messages/tr.json`, alongside the existing `draftRow.toast*` keys:

```json
"toastApprovedWaiting": "Approved — will send automatically once today's sending limit resets"
```

(Turkish translation added in the same PR, matching the existing key-parity convention in these files.)

## 9. Testing plan

- `markEmailWaiting` / `getSequenceByLeadId`: unit tests, mirroring `markEmailFailed`'s and existing `sequences.ts` function tests.
- `processLead`/`runWriteForCase`: extend existing write.ts tests — `RATE_LIMITED` now returns `'waiting'` and marks the row `waiting`, not `failed`; new case-status test for the `waiting > 0` → `awaiting_resend` branch; new test for the per-lead pre-filter skipping a lead that already has a `'waiting'` row (and never calling the LLM mock for it).
- `approveDraft`: update the 2026-08-19 RATE_LIMITED tests — now assert `markEmailWaiting` + `updateCaseWaiting(..., 'awaiting_resend')` + a normal return (not a rethrow), and the new `{ status: 'waiting' }` shape.
- `runFollowupStep`: new tests for the `RATE_LIMITED` catch — asserts `markEmailWaiting`, asserts **no** `publishJsonWithDelay` call (distinguishing it from the paused-campaign reschedule branch already tested).
- `resend-failed.ts`: existing first-touch tests updated for the status rename (`failed` → `waiting` in fixtures/queries); new tests for the `sequence_step > 0` branch — resend as-is, correct `inReplyTo`/`threadId` recomputation, sequence advance vs. exhaustion-and-case-dead paths, and the `RATE_LIMITED`-stays-`waiting` vs. genuine-error-goes-`failed` distinction.
- `draft-row.tsx`: test both toast paths render distinctly for `status: 'sent'` vs `status: 'waiting'`.
- Full suite + `tsc --noEmit` + `eslint` at each step, per project standard.

2. `markEmailWaiting`, `getSequenceByLeadId`, `listWaitingLeadIds` — small, independently testable primitives.
3. `write.ts` swap (processLead catch + per-lead pre-filter + post-loop branch).
4. `approveDraft` swap + `draft-row.tsx` toast + i18n strings.
5. `followup.ts` swap.
